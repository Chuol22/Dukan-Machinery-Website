# Requirements Document

## Introduction

This feature adds a comprehensive set of admin dashboard enhancements to the existing DKM Machinery Next.js 16 + Prisma + PostgreSQL + Tailwind CSS application. The enhancements include: new Prisma schema models (Customer, MachineInquiry, Quotation) and schema changes (Order timeline, Machine status); a Machine Inquiry system with public and admin interfaces; a Customer Management admin page; a Quotation System with PDF generation and email delivery via Nodemailer; an Analytics Dashboard with Recharts charts; an Enhanced Notification Center with a bell dropdown; Admin Sidebar updates; and a multi-state Machine Status system replacing the boolean `is_available` field.

The implementation must extend existing components (OrdersClient.tsx, MachinesClient.tsx, AdminLayoutClient.tsx) rather than replacing them, follow existing coding patterns (Prisma singleton at `lib/prisma.ts`, admin session verification via `verifyAdminSession` from `lib/auth.ts`, Tailwind CSS + dark mode), and integrate with existing Nodemailer and Cloudinary configurations.

---

## Glossary

- **Admin**: An authenticated user with `SUPER_ADMIN` or `SALES_OFFICER` role accessing `/admin` pages.
- **Customer**: A record in the `Customer` table representing a business contact identified by unique email, auto-created or updated on order or inquiry submission.
- **MachineInquiry**: A pre-sales inquiry submitted by a visitor asking about a specific machine or a general question.
- **Inquiry_API**: The Next.js API route handler that processes machine inquiry submissions and admin management.
- **Quotation**: A formal price proposal generated by an admin from an order, with associated PDF and email delivery.
- **Quotation_PDF**: A PDF document generated using `@react-pdf/renderer` containing company info, cost breakdown, terms, and authorization sections.
- **Order_Status_Pipeline**: The ordered sequence of statuses an order passes through: `new` → `pending` → `quotation_sent` → `accepted` → `rejected` → `completed`.
- **Machine_Status**: A string enum replacing the boolean `is_available` field; valid values are `available`, `reserved`, `out_of_stock`, `maintenance`, `coming_soon`, `discontinued`.
- **Analytics_API**: The Next.js API route at `/api/admin/analytics` that aggregates data for the dashboard charts.
- **Notification_Center**: The bell icon in the admin header that shows unread count and a dropdown of the latest 5 notifications.
- **Dashboard**: The admin landing page at `/admin` showing stats cards and Recharts charts.
- **Recharts**: The charting library used for all analytics visualizations.
- **Nodemailer**: The email library configured with `EMAIL_USER` / `EMAIL_PASS` env vars used to send quotation PDFs.

## Requirements

### Requirement 1: Prisma Schema — Customer Model

**User Story:** As an Admin, I want customer contact records to be automatically maintained, so that I can see a consolidated view of all business contacts without manual data entry.

#### Acceptance Criteria

1. THE System SHALL define a `Customer` model in the Prisma schema with fields: `id` (UUID PK), `name` (String), `company` (String, optional), `country` (String, optional), `phone` (String, optional), `email` (String, unique), `total_orders` (Int, default 0), `last_order_date` (DateTime, optional), `status` (String, default `"active"`), `created_at` (DateTime), `updated_at` (DateTime, auto-updated).
2. THE System SHALL define a relation from `Customer` to `Order` (one Customer to many Orders via `customer_id` FK on Order).
3. THE System SHALL define a relation from `Customer` to `MachineInquiry` (one Customer to many MachineInquiries via `customer_id` FK on MachineInquiry).
4. WHEN an Order is created or updated, THE System SHALL upsert a Customer record matching the order's `customer_email`, incrementing `total_orders` and updating `last_order_date`.
5. WHEN a MachineInquiry is submitted, THE System SHALL upsert a Customer record matching the inquiry's `email`, updating `name`, `phone`, and `company` if provided.

---

### Requirement 2: Prisma Schema — MachineInquiry Model

**User Story:** As an Admin, I want to track pre-sales inquiries linked to specific machines and customers, so that I can manage the sales pipeline from first contact.

#### Acceptance Criteria

1. THE System SHALL define a `MachineInquiry` model with fields: `id` (UUID PK), `customer_id` (UUID FK to Customer, nullable), `machine_id` (UUID FK to Machine, nullable), `machine_name` (String), `customer_name` (String), `email` (String), `phone` (String, optional), `message` (String), `status` (String, default `"new"`; valid values: `new`, `replied`, `closed`), `created_at` (DateTime), `updated_at` (DateTime, auto-updated).
2. THE System SHALL index `MachineInquiry` on `status`, `email`, and `created_at` (descending).

---

### Requirement 3: Prisma Schema — Order Model Changes

**User Story:** As an Admin, I want the Order model to support a multi-step status pipeline and link to a Customer record, so that I can track the full sales lifecycle.

#### Acceptance Criteria

1. THE System SHALL add a `customer_id` (UUID FK to Customer, nullable, `onDelete: SetNull`) field to the `Order` model.
2. THE Order_Status_Pipeline SHALL support the following string status values: `new`, `pending`, `quotation_sent`, `accepted`, `rejected`, `completed`.
3. THE System SHALL add a relation from `Order` to `Quotation` (one Order to many Quotations).

---

### Requirement 4: Prisma Schema — Machine Status Change

**User Story:** As an Admin, I want fine-grained machine availability statuses instead of a boolean, so that I can accurately communicate machine state to customers.

#### Acceptance Criteria

1. THE System SHALL retain the `is_available` boolean field on the `Machine` model for backwards compatibility while adding a new `availability_status` String field (default `"available"`; valid values: `available`, `reserved`, `out_of_stock`, `maintenance`, `coming_soon`, `discontinued`).
2. WHEN the `availability_status` field is set to `"out_of_stock"`, THE System SHALL automatically set `is_available` to `false`.
3. WHEN the `availability_status` field is set to any value other than `"out_of_stock"`, `"maintenance"`, or `"discontinued"`, THE System SHALL set `is_available` to `true`.

---

### Requirement 5: Prisma Schema — Quotation Model

**User Story:** As an Admin, I want to store quotation records with cost breakdown details, so that I can track issued quotations and their acceptance status.

#### Acceptance Criteria

1. THE System SHALL define a `Quotation` model with fields: `id` (UUID PK), `order_id` (UUID FK to Order), `quotation_number` (String, unique), `machine_cost` (Float), `shipping_cost` (Float, default 0), `installation_cost` (Float, default 0), `additional_charges` (Float, default 0), `total_cost` (Float), `valid_until` (DateTime), `terms` (String, optional), `status` (String, default `"draft"`; valid values: `draft`, `sent`, `negotiating`, `approved`, `rejected`), `pdf_url` (String, optional), `created_at` (DateTime), `updated_at` (DateTime, auto-updated).
2. THE System SHALL index `Quotation` on `order_id` and `quotation_number`.

### Requirement 6: Machine Inquiry — Public Submission

**User Story:** As a Visitor, I want to submit a machine inquiry from the machine detail page or a standalone inquiry page, so that I can ask questions about specific machines without placing a full order.

#### Acceptance Criteria

1. WHEN a visitor views the `/machines/[slug]` page, THE System SHALL display an "Ask a Question" button that opens an inline form with the machine name pre-filled.
2. THE Inquiry_API SHALL expose a `POST /api/inquiries` endpoint accessible without authentication that accepts: `customer_name` (required), `email` (required, valid email format), `phone` (optional), `machine_name` (optional), `machine_id` (optional UUID), `message` (required, minimum 10 characters).
3. IF the submitted `POST /api/inquiries` payload is missing required fields or contains an invalid email, THEN THE Inquiry_API SHALL return HTTP 400 with a descriptive error message.
4. WHEN a valid inquiry is submitted via `POST /api/inquiries`, THE Inquiry_API SHALL create a `MachineInquiry` record with `status = "new"`, upsert a `Customer` record by email, and create a `Notification` record with `type = "new_inquiry"`.
5. THE System SHALL serve a standalone `/inquiry` page containing a full inquiry form with fields: Customer Name, Email, Phone, Machine (text input, with pre-fill from query param `?machine=<name>` available when the parameter is present), Message.
6. WHEN a valid inquiry is submitted successfully, THE System SHALL display a confirmation message to the visitor without navigating away from the page.

---

### Requirement 7: Machine Inquiry — Admin Management

**User Story:** As an Admin, I want to view and manage all machine inquiries with status controls, so that I can track and respond to pre-sales questions.

#### Acceptance Criteria

1. THE System SHALL expose a `GET /api/admin/inquiries` endpoint (admin-authenticated) that returns all MachineInquiry records ordered by `created_at` descending, including associated `customer_name`, `email`, `phone`, `machine_name`, `status`, and `created_at`.
2. THE System SHALL expose a `PUT /api/admin/inquiries/[id]` endpoint (admin-authenticated) that accepts a `status` field with valid values `new`, `replied`, or `closed` and updates the MachineInquiry record accordingly.
3. IF an unauthenticated request is made to `GET /api/admin/inquiries` or `PUT /api/admin/inquiries/[id]`, THEN THE Inquiry_API SHALL return HTTP 401 regardless of the reason authentication failed (including timeouts or cookie errors).
4. THE System SHALL provide an `/admin/inquiries` page listing all inquiries in a table with columns: Customer Name, Email, Phone, Machine, Message (truncated), Status, Date, and an Actions column.
5. WHEN an Admin changes an inquiry status from the `/admin/inquiries` page, THE System SHALL send a toast notification confirming the action, including when the submitted status value matches the current status.

### Requirement 8: Customer Management — Admin Page

**User Story:** As an Admin, I want a dedicated customer list page, so that I can see all contacts and their order activity at a glance.

#### Acceptance Criteria

1. THE System SHALL expose a `GET /api/admin/customers` endpoint (admin-authenticated) that returns all Customer records including: `id`, `name`, `company`, `country`, `phone`, `email`, `total_orders`, `last_order_date`, `status`, `created_at`.
2. IF an unauthenticated request is made to `GET /api/admin/customers`, THEN THE System SHALL return HTTP 401.
3. THE System SHALL provide an `/admin/customers` page displaying a sortable table of all customers with columns: Name, Company, Country, Phone, Email, Total Orders, Last Order Date, Status. WHEN the API call fails with any error including HTTP 401, THE System SHALL still render the table structure (with an empty or error state row) rather than redirecting.
4. WHEN an Admin views `/admin/customers`, THE System SHALL display a status badge for each customer using the values `active` (green) or `inactive` (gray).
5. THE System SHALL include a search input on `/admin/customers` that filters the customer list client-side by name, email, or company.

### Requirement 9: Quotation System — Creation and PDF Generation

**User Story:** As an Admin, I want to create a quotation from an order and generate a professional PDF, so that I can send formal price proposals to customers.

#### Acceptance Criteria

1. WHEN an Admin views an order detail, THE System SHALL display a "Create Quotation" button if no quotation with status `sent`, `approved`, or `negotiating` exists for that order.
2. THE System SHALL present a quotation form with fields: Machine Cost, Shipping Cost, Installation Cost, Additional Charges (all numeric, required), Total Cost (auto-calculated as sum of all cost fields), Valid Until (date picker, required), Terms (textarea, optional).
3. WHEN an Admin submits a valid quotation form, THE System SHALL call `POST /api/admin/orders/[id]/quotation` which creates a `Quotation` record with `status = "draft"`, generates a `quotation_number` in the format `QT-<year>-<sequential-number>` (e.g. `QT-2025-0042`), and generates a Quotation_PDF.
4. THE Quotation_PDF SHALL contain: company logo, company name and contact info, quotation number, issue date, valid until date, customer name/company/contact, machine name and quantity, cost breakdown table (machine cost, shipping, installation, additional charges, total), terms and conditions, a warranty information section, an authorized signature section, a company stamp/seal section, and a thank you message.
5. WHEN the Quotation_PDF is generated, THE System SHALL upload it to Cloudinary via the existing `/api/upload` pattern and store the resulting URL in `Quotation.pdf_url`.
6. WHEN the quotation is created and the PDF is ready, THE System SHALL send the Quotation_PDF as an email attachment to the customer's email using Nodemailer with `EMAIL_USER` / `EMAIL_PASS` credentials, update the `Order.status` to `"quotation_sent"`, and update `Quotation.status` to `"sent"`.
7. IF the Nodemailer send operation fails, THEN THE System SHALL return HTTP 500 with a descriptive error and NOT update the Order or Quotation status.
8. THE System SHALL expose `POST /api/admin/orders/[id]/quotation` as an admin-authenticated endpoint; IF the request is unauthenticated, THEN THE System SHALL return HTTP 401.

### Requirement 10: Analytics Dashboard

**User Story:** As an Admin, I want an analytics dashboard with charts and stats cards, so that I can understand business performance at a glance without running manual queries.

#### Acceptance Criteria

1. THE System SHALL expose a `GET /api/admin/analytics` endpoint that applies all data aggregation and validation constraints only when the requester is admin-authenticated, returning aggregated data for: total orders count, pending orders count, accepted orders count, rejected orders count, total machines count, available machines count, total customers count, orders per month (last 12 months), top 5 most-ordered machines by order item count, order status distribution (count per status), customer growth by month (last 12 months), machine availability distribution (count per `availability_status`), and inquiry count per month (last 12 months).
2. IF an unauthenticated request is made to `GET /api/admin/analytics`, THEN THE System SHALL return HTTP 401.
3. THE System SHALL update the `/admin` page to display the following stats cards: Total Orders, Pending Orders, Accepted Orders, Rejected Orders, Total Machines, Available Machines, Total Customers.
4. THE System SHALL render the following Recharts charts on the `/admin` page:
   - A `BarChart` showing orders per month for the last 12 months (x-axis: month label, y-axis: order count).
   - A horizontal `BarChart` showing the top 5 most-requested machines (x-axis: order count, y-axis: machine name).
   - A `PieChart` showing order status distribution.
   - A `LineChart` showing customer growth by month for the last 12 months.
   - A `PieChart` showing machine availability distribution.
   - An `AreaChart` showing inquiry trends over the last 12 months.
5. WHEN the Analytics_API returns data, THE System SHALL render charts client-side using the `"use client"` directive and Recharts components with `ResponsiveContainer` for fluid width.
6. WHILE analytics data is loading, THE System SHALL display skeleton placeholder elements for each chart and stats card.

### Requirement 11: Enhanced Notification Center

**User Story:** As an Admin, I want a bell icon in the header with a live unread count and dropdown preview, so that I can see new activity without navigating to the full notifications page.

#### Acceptance Criteria

1. THE System SHALL extend the existing `Notification` model usage to support the following `type` values: `new_order`, `new_inquiry`, `new_review`, `inventory_alert`, `order_status_change`.
2. THE System SHALL replace the static bell link in the admin header with a `NotificationBell` client component that fetches unread notification count every 30 seconds via `GET /api/admin/notifications`.
3. WHEN the unread notification count is greater than 0, THE NotificationBell SHALL display a count badge over the bell icon showing the exact count (capped at display of "9+" if count exceeds 9).
4. WHEN an Admin clicks the bell icon, THE NotificationBell SHALL display a dropdown panel listing the latest 5 notifications with: notification title, truncated message (max 80 characters), relative timestamp, and a link to the relevant admin page.
5. THE NotificationBell dropdown SHALL include a "View all notifications" link to `/admin/notifications`.
6. WHEN an Admin clicks a notification in the dropdown, THE System SHALL mark it as read via `PUT /api/admin/notifications` and navigate to the relevant link.
7. WHEN a machine's `availability_status` is changed to `"out_of_stock"` via the admin API, THE System SHALL always create a `Notification` record with `type = "inventory_alert"` and a message including the machine name, regardless of existing unread notification count.

### Requirement 12: Admin Sidebar Updates

**User Story:** As an Admin, I want the sidebar to include navigation links for the new pages, so that I can access Customers, Inquiries, and Analytics without typing URLs manually.

#### Acceptance Criteria

1. THE AdminLayoutClient SHALL add a "Customers" nav item linking to `/admin/customers` with an appropriate icon (e.g. `Users` from lucide-react) under the "Sales & Orders" section.
2. THE AdminLayoutClient SHALL add an "Inquiries" nav item linking to `/admin/inquiries` with an appropriate icon (e.g. `MessageSquare` from lucide-react) under the "Sales & Orders" section.
3. THE AdminLayoutClient SHALL add an "Analytics" nav item linking to `/admin/analytics` with an appropriate icon (e.g. `BarChart2` from lucide-react) under the "Overview" section.
4. THE AdminLayoutClient header breadcrumb SHALL display appropriate page titles for the new pages: `"Customers"` when `pathname` starts with `/admin/customers`, `"Inquiries"` when `pathname` starts with `/admin/inquiries`, `"Analytics"` when `pathname === '/admin/analytics'`.
5. WHEN the current pathname matches one or more nav item hrefs, THE System SHALL apply the active highlight style (orange background) to all matching nav items, consistent with existing nav item behavior. No visual indication is applied when the pathname does not match any nav item.

### Requirement 13: Machine Status Management — Admin UI

**User Story:** As an Admin, I want to set a machine's availability status from a dropdown with six options instead of a toggle, so that I can accurately represent the machine's current state.

#### Acceptance Criteria

1. THE MachinesClient SHALL replace the availability toggle button with a status dropdown displaying the six Machine_Status options: Available, Reserved, Out of Stock, Maintenance, Coming Soon, Discontinued.
2. THE System SHALL display a color-coded badge for each Machine_Status value in the machine table: Available (green), Reserved (blue), Out of Stock (red), Maintenance (amber), Coming Soon (purple), Discontinued (gray).
3. WHEN an Admin changes a machine's status from the dropdown in MachinesClient, THE System SHALL call `PUT /api/machines/[id]` with the updated `availability_status` value and apply an optimistic update to the table row.
4. THE `/api/machines/[id]` PUT handler SHALL accept the `availability_status` field and update both `availability_status` and `is_available` in the database in a single Prisma call, applying the rule from Requirement 4, Criteria 2–3.
5. WHEN the `availability_status` is updated to `"out_of_stock"` via the API, THE System SHALL create a `Notification` record with `type = "inventory_alert"` referencing the machine name, consistent with Requirement 11, Criteria 7.
